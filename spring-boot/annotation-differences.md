# Difference Between `@Component`, `@Service`, `@Repository`, and `@Controller`

## 1. Introduction

In Spring Framework, `@Component`, `@Service`, `@Repository`, and `@Controller` are **stereotype annotations** used to identify classes that play specific roles in an application.

All four can make classes eligible for Spring component scanning and registration as Spring beans. However, they communicate different responsibilities, and some provide additional framework-specific behavior.

## 2. Explanation with examples

### A. `@Component` — General-purpose component

Used to mark a class as a Spring-managed component when it does not belong to a more specific application layer.

```java
@Component
public class EmailValidator {

    public boolean isValid(String email) {
        return email != null && email.contains("@");
    }
}
```

**Typical use cases:**
- Utility components
- Custom validators
- Helper classes
- Generic application components

### B. `@Service` — Business logic layer

Used to identify a class that implements business logic or coordinates application operations.

```java
@Service
public class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public String getUser(Long id) {
        return userRepository.findById(id);
    }
}
```

**Typical use cases:**
- Business rules and validations
- Coordinating repository calls
- Application workflows
- Transactional business operations

`@Service` primarily communicates the class's role. It does not automatically make every method transactional.

### C. `@Repository` — Data access layer

Used to identify classes responsible for accessing and persisting data.

```java
@Repository
public class UserRepository {

    public String findById(Long id) {
        // Database query would be performed here.
        return "User " + id;
    }
}
```

**Typical use cases:**
- Database operations
- Persistence logic
- Queries and data retrieval
- Data storage and updates

**Important difference:** `@Repository` can enable Spring's persistence exception translation for eligible repository beans when the required infrastructure is configured.

With Spring Data JPA, repository implementations are commonly generated by Spring Data rather than written manually.

### D. `@Controller` — Web presentation layer

Used to identify a Spring MVC controller that handles incoming web requests. It commonly returns a view name for server-side rendering.

```java
@Controller
public class HomeController {

    @GetMapping("/home")
    public String home(Model model) {
        model.addAttribute("message", "Welcome!");
        return "home";
    }
}
```

**Typical use cases:**
- Handling HTTP requests
- Processing web input
- Returning view names
- Preparing model data for server-rendered pages

For REST APIs, `@RestController` is commonly used. It combines `@Controller` and `@ResponseBody`, so handler return values are written to the HTTP response body by default.

## 3. Key differences

| Feature | `@Component` | `@Service` | `@Repository` | `@Controller` |
|---|---|---|---|---|
| Purpose | General component | Business logic | Data access | Web request handling |
| Typical layer | Any layer | Service layer | Persistence layer | Presentation layer |
| Component scanning | Yes | Yes | Yes | Yes |
| Specialized behavior | General stereotype | Primarily communicates role | Supports persistence exception translation | Integrates with Spring MVC handler infrastructure |
| Common example | `EmailValidator` | `UserService` | `UserRepository` | `UserController` |

## 4. How are these annotations related?

`@Service`, `@Repository`, and `@Controller` are specialized stereotype annotations built on top of `@Component`.

Conceptually, the application layers work together like this:

```text
Client
  |
  v
@Controller
  |
  v
@Service
  |
  v
@Repository
  |
  v
Database
```

For example, when a client requests a user's details:

1. `@Controller` receives the HTTP request.
2. `@Service` executes the business logic.
3. `@Repository` retrieves the user's data.
4. The result returns to the controller.
5. The controller sends the appropriate response to the client.

This is a common architectural pattern, not a mandatory rule. An application may have additional components or use different architectural boundaries.

## 5. Can we use `@Component` instead of `@Service` or `@Repository`?

Technically, `@Component` can be used for many classes that would otherwise use `@Service` or `@Repository`, provided the class is registered correctly.

However, using the more specific annotation is preferable because it:

- Communicates the class's responsibility clearly.
- Makes the architecture easier to understand.
- Allows specialized framework behavior where applicable, particularly persistence exception translation for repositories.

Also, avoid stacking multiple stereotype annotations on the same class just to provide extra context. Choose the annotation that best describes the class's role.

## 6. Interview-ready answer

**Question: What is the difference between `@Component`, `@Service`, `@Repository`, and `@Controller`?**

All four are Spring stereotype annotations used to identify classes for Spring bean registration through component scanning.

`@Component` is a general-purpose annotation. `@Service` identifies the business logic layer, `@Repository` identifies the data access layer and supports persistence exception translation, and `@Controller` identifies the web presentation layer for handling requests.

The main difference is their intended responsibility and, in some cases, their specialized framework behavior. I use these annotations to maintain a clear separation of concerns in a layered Spring Boot application.

## Quick revision

- **`@Component`** — General-purpose Spring-managed component.
- **`@Service`** — Business logic.
- **`@Repository`** — Data access and persistence exception translation.
- **`@Controller`** — Spring MVC request handling.
- **`@RestController`** — Controller whose return values are written to the response body by default.
- All four can participate in Spring component scanning; use the most specific annotation for clarity.

# Difference Between `@Controller` and `@RestController` in Spring Boot

## 1. What is `@Controller`?

`@Controller` is a Spring MVC stereotype annotation used to define a controller that handles incoming HTTP requests.

It is commonly used in **server-side web applications** where controller methods return view names, such as Thymeleaf templates, or `ModelAndView` objects.

### Example

```java
@Controller
public class HomeController {

    @GetMapping("/home")
    public String home(Model model) {
        model.addAttribute("message", "Welcome to Spring Boot!");
        return "home";
    }
}
```

### How does it work?

1. The client sends a GET request to `/home`.
2. Spring MVC routes the request to the `home()` method.
3. The controller adds data to the `Model`.
4. The method returns `"home"`, which Spring MVC treats as a view name.
5. A configured view resolver resolves the view, which is rendered and returned to the client.

**Important:** With `@Controller`, a returned string is generally interpreted as a view name unless `@ResponseBody` is applied.

## 2. What is `@RestController`?

`@RestController` is a specialized Spring annotation that combines `@Controller` and `@ResponseBody`.

It is commonly used to build REST APIs, where handler method return values are written directly to the HTTP response body instead of being interpreted as view names.

### Example

```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        return new User(1L, "Danish");
    }
}
```

Assuming `User` is a suitable Java object and the required JSON message converter is available, a request to `/api/users/1` could return:

```json
{
  "id": 1,
  "name": "Danish"
}
```

### How does it work?

1. The client sends an HTTP GET request.
2. Spring MVC routes it to the controller method.
3. The method returns a Java object.
4. An appropriate `HttpMessageConverter`, commonly Jackson for JSON, serializes the object.
5. Spring sends the serialized result in the HTTP response body with an appropriate content type.

## 3. Key differences

| Feature | `@Controller` | `@RestController` |
|---|---|---|
| Primary use | Web pages and MVC applications | REST APIs |
| Annotation composition | Spring MVC controller stereotype | `@Controller` + `@ResponseBody` |
| Default return-value behavior | Often resolves a view name | Writes the return value to the response body |
| Typical response | HTML rendered from a view | JSON, XML, text, or another supported representation |
| `Model` support | Commonly used for view rendering | Can be used, but is not required for response-body handling |
| Common use case | Thymeleaf-based web application | Backend API for Angular or React |

## 4. Can `@Controller` return JSON?

Yes. Add `@ResponseBody` to a handler method or use it at the class level.

```java
@Controller
public class UserApiController {

    @ResponseBody
    @GetMapping("/api/user")
    public User getUser() {
        return new User(1L, "Danish");
    }
}
```

Here, the returned `User` object is serialized into the HTTP response body rather than being interpreted as a view name.

This is the key reason `@RestController` is convenient for REST APIs: you do not need to add `@ResponseBody` to every handler method.

## 5. Can `@RestController` return plain text?

Yes. The response body does not have to be JSON.

```java
@RestController
public class MessageController {

    @GetMapping("/message")
    public String getMessage() {
        return "Hello, World!";
    }
}
```

The response body is:

```text
Hello, World!
```

The returned string is written directly to the response body; Spring does not try to find a view named `Hello, World!`.

## 6. What if I want to return a view from `@RestController`?

Because `@RestController` applies response-body behavior by default, returning `"home"` normally sends the literal text `home` rather than rendering the `home` template.

For traditional view rendering, use `@Controller`. Alternatively, you can explicitly configure a handler method to resolve a view, but using `@Controller` is generally clearer.

## 7. Interview-ready answer

**Question: What is the difference between `@Controller` and `@RestController`?**

Both annotations are used to handle HTTP requests in Spring MVC. The main difference is how they handle method return values.

`@Controller` is generally used in traditional MVC applications where a method returns a view name or a `ModelAndView` object that Spring resolves and renders.

`@RestController` combines `@Controller` and `@ResponseBody`. It writes handler return values directly to the HTTP response body, typically serializing Java objects into JSON using an appropriate message converter.

For example, I use `@Controller` for a Thymeleaf-based web application and `@RestController` when developing REST APIs consumed by an Angular or React frontend.

## Quick revision

- `@Controller` → commonly returns a view name.
- `@RestController` → response-body behavior by default.
- `@RestController` = `@Controller` + `@ResponseBody`.
- `@ResponseBody` can make an individual `@Controller` method return data directly.
- `HttpMessageConverter` handles response-body serialization.
- Choose the annotation according to whether the handler should render a view or return response data.
